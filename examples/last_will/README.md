# Last Will Simplex Example

This example builds on [`examples/basic`](../basic). Where `p2pk.simf`
there is a single spending condition, `last_will.simf` is a recursive
covenant: it re-creates itself on-chain across a series of transactions,
and offers three spending actions depending on which key signs.

When its tests are run with `-v`, this example adds narration to give
more context about the actions each test is performing.

## Overview

`last_will.simf` implements a simple inheritance scheme with three keys
and an inheritance distance, all supplied to the contract as `param::`
arguments:

* **Inherit**: after the covenant sits untouched for
  `param::INHERITANCE_DISTANCE` blocks (relative timelock), the inheritor's
  key can withdraw the funds. The upstream contract hardcodes 25920 blocks,
  about 18 days at Liquid's 1-minute block time; this example passes 1440
  instead, so the tests can mine it.
* **ColdSpend**: the owner's cold key can break out of the covenant at any
  time, with no wait required.
* **HotSpend**: the owner's hot key can spend at any time, which resets
  the inheritance clock. `refresh_spend` checks a signature and then calls
  `recursive_covenant()`, which requires the transaction to pay back into
  the same covenant script (output 0) alongside an Elements fee output
  (output 1). Bitcoin Script has no equivalent, because it cannot inspect
  a transaction's outputs.

For Simplex compatibility, these actions are represented here as Either
types (instantiated with Left/Right) rather than named `enum` values.

### Keys

The three keys are ordinary Simplex wallets. `tests/last_will_test.rs`
builds one per party with `TestContext::create_signer`, each from its own
BIP-39 mnemonic, the same way `Simplex.toml`'s `[test] mnemonic` produces
the default test wallet:

```rust
let inheritor = context.create_signer(INHERITOR_MNEMONIC);
```

Their public keys become the contract's `param::INHERITOR_PK`,
`param::COLD_PK` and `param::HOT_PK`, alongside
`param::INHERITANCE_DISTANCE`. The covenant's script, and therefore its
address, is derived from all four;
`hot_spend_wrong_continuation_script_fails` relies on that, refreshing into
a covenant with the same three keys but a doubled inheritance distance,
which the contract rejects.

Spending uses Simplex's signing path: the witness carries a placeholder
signature at the branch being taken,
`RequiredSignature::witness_with_path` says where the signature belongs,
and the signer fills it in.

The mnemonics in the test file are standard BIP-39 test vectors, so
their keys are public. Generate your own secrets for any deployment
holding real funds.

### Outputs and fees

The tests give Simplex the input and a change target. Simplex appends the
change output, then an Elements fee output, and works out both amounts:

```rust
ft.add_change(ChangeOutput::new(script.clone()));
```

For a **HotSpend** the change target is the covenant's own script, which
produces the two outputs `recursive_covenant()` requires: output 0 paying
back into the same covenant, output 1 the fee. For **ColdSpend** and
**Inherit** the contract places no constraints on outputs, so the change
target is the spending party's wallet.

Three tests check that the covenant rejects a malformed output set: one
with a single output, one with a non-fee output at index 1, and one with
the fee and continuation outputs swapped. A change target cannot produce
those shapes, because Simplex always appends change first and fee second,
so those tests list their outputs directly and sign with `Signer::sign_tx`,
which appends nothing.

The repository structure is the same shape as `examples/basic`:

```md
root
├── simf — Simplicity smart contracts source directory
├── src — The project's Rust code (witness and transaction builders)
│   └── artifacts — Simplicity artifacts generated by Simplex (gitignored)
├── tests — Simplex tests directory
├── Cargo.toml — The project's Rust configuration
└── Simplex.toml — The project's Simplex configuration
```

### Build

```bash
simplex build
```

As with `examples/basic`, this generates `src/artifacts`, already declared
as a module in `src/lib.rs`.

### Test

```bash
simplex test -v
```

The `-v` option adds verbose output. The test suite includes narration,
with each test showing what it's attempting and how the network
responded. Several tests expect a rejection (wrong key, broken
`recursive_covenant()` check, or inheritance claimed too early).

One test, `inherit_after_wait_succeeds`, synthetically mines 1440 blocks
to make the inheritance wait real. This should be relatively rapid with
local `elementsd`.

### Low-level tracing

To see a local trace of the SimplicityHL contract executing in each test,
run the tests with an extra `-v`:

```bash
simplex test -vv
```

This shows the individual
[jet](https://docs.simplicity-lang.org/documentation/jets) calls during
the course of the contract's execution, with their input and output
values. You can use this information to follow the contract's own logic
during a real transaction validation. For example, in the test cases that
exercise invalid spend conditions, you can see where the failures and
rejections happened.
