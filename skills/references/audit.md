# Auditing a finite spending predicate

Simplicity executes a typed, finite DAG. SimplicityHL functions and bounded iteration compile into that model. Audit the authorization predicate and its transaction dependencies. Solidity reentrancy, delegate calls, account storage slots and unbounded runtime loops are not standalone Simplicity attack surfaces. Off-chain transaction builders and host applications need a separate scope.

## Establish the policy and trust map

For each spend branch, record the authorized actors, required signatures, signed messages, locks, consumed UTXOs and protected successor outputs. Distinguish deployment parameters and committed constants from free witnesses and transaction fields. An attacker may choose witnesses, add other inputs, rearrange outputs and select transaction fields unless the predicate or signature binds them. A successful assertion proves only that assertion, not the intended end-to-end property.

Use the supplied requirements to derive properties. Separate explicit guarantees from exploratory assumptions. For example, a signature-only spend intentionally permits arbitrary outputs; a renewal covenant may preserve a script without guaranteeing value unless the policy says otherwise. Intentionally omitted sighash fields, authorized exits and cooperative branches remaining available after a refund threshold are not findings by themselves.

## Check the relations across every relevant branch

- **Authority and messages:** trace each verification key to its commitment. A valid signature by a witness-selected key proves control of that key, not permission from the contract owner. Identify the complete digest: transaction authorization, oracle data and domain-separated external messages have different purposes. Check ordered serialization, widths and all intended message fields. Changing a protected transaction output after signing should invalidate a full-transaction signature. A signature over a constant or partial digest cannot substitute for it.
- **Time and scope:** check which branch needs the lock. Use transaction lower bounds, not witness assertions of current height. Relative blocks require version >= 2 and the current input's parsed sequence, with disable/time flags handled. An unrelated input must not grant this UTXO's delay. Old aggregate distance/duration jets are unsafe; see [timelocks.md](timelocks.md). Offline program execution does not establish actual UTXO age or exact block inclusion. An upper deadline cannot be enforced by choosing a small nLockTime.
- **Outputs and state:** bind index, existence, script, asset and amount where the policy requires them. Script equality alone does not preserve a balance. Inspect explicit/confidential sum branches and unwrap types. Fee outputs and separate fee inputs are policy-dependent. A claimed state transition is enforced only if the next output commits the intended state; a witness naming that state is insufficient. For coupled input contracts, confirm the actual shared layout instead of assuming another predicate performs the missing check.
- **Conservation and arithmetic:** express payment/burn/release quantities as equations, then locate the checks for every term. Exact division needs both quotient and zero remainder. Jet add/subtract flags and multiplication high limbs are data that must be checked when narrowing. Determine rounding direction, zero denominators and permitted numeric ranges. A wide result is not automatically safe if later reduced to a smaller word. Avoid alleging an overflow without concrete values that reach the acceptance path.

## Seek executable counterexamples

Choose tests from policy relationships, not from restating existing assertions. Include a valid case so unconditional rejection does not pass the suite. Change one dimension at a time: authorized versus wrong key, absent/invalid signature, transaction mutation, lock threshold minus/at/plus one, wrong units or flags, current versus other input, wrong asset/script, exact ratio versus nonzero remainder, and word-boundary arithmetic. Preserve minimal concrete values and tool output. Use the provided execution harness if one is available; otherwise the bundled fixture and [testing.md](testing.md) support normal Simplex tests.

Confirm the compiler actually processes the intended source. Source discovery warns about unparseable files; inspect metadata and diagnostics to establish coverage. Distinguish successful compilation, witness satisfaction, BitMachine execution and node consensus. A missing witness rejected before execution is not a proof that the branch's arithmetic is safe. Multi-step properties require linked UTXOs and committed successor states, not arbitrary independent snapshots.

## Calibrate the report

For a confirmed security finding, name the violated property, source location, attacker controls, reachable path, concrete witness/transaction values, impact and fix. Say whether evidence is executed or reasoned. Follow sibling branches for the same root cause and deduplicate findings that require the same fix. Keep plausible but unverified leads separate. Report ordinary correctness/specification errors separately from unauthorized spend, asset loss or adversarial freezing. State coverage gaps and tool failures; a completion declaration is not a security verdict.
